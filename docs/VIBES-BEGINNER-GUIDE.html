Upgrade Mule apps to Java 17 with the Vibes Agent

Set up this toolkit from a blank machine, prove it works from the terminal first, then load it into MuleSoft Vibes and test every single skill by chatting. Every term is explained; every command is copy-ready.

What you'll end up with: a chat assistant inside your MuleSoft editor. You say “help me upgrade a Mule app to Java 17,” and it walks you through it — asks a few questions, shows exactly what it plans to change, waits for your “yes,” then opens a pull request and tracks the deployment. Nothing is changed without your approval.

The plan in one line: install & self-check (Steps 1–3) → configure the one .env (Step 4) → verify every integration + every skill from the terminal (Steps 5–6) → link all skills into Vibes and reload (Steps 7–8) → test every skill by chatting (Step 9) → confirm it worked (Step 10). Doing the terminal pass first separates “is the toolkit healthy?” from “is Vibes wired?” — so if something breaks later you already know which half to look at.

1. What this is, in plain English

Old MuleSoft applications run on older versions of Java (8 or 11). Support for those is ending, so every app must move to Java 17 on the Mule runtime 4.9.18 LTS. Doing that by hand — walking the pom files, bumping connector versions, editing mule-artifact.json and CI workflows, testing, raising a pull request, tracking the deploy — is slow and error-prone.

This toolkit automates it. It comes in two shapes that share the same engine underneath:

SkillsSmall helpers the Vibes assistant runs for you. This is what this guide sets up.
An MCP serverAn optional always-on service exposing the same abilities as network “tools” (used for Agentforce, or when Vibes sandboxes scripts). Covered as an alternative in Step 6/the server section.

The star of the show is the interactive agent (a skill named mule-upgrade-agent). Instead of you memorising commands, it holds a conversation and follows a fixed, safe sequence:

  1. Source — read the app from a folder on your computer (local), or straight from GitHub (api).
  2. Location — the folder path, or the GitHub owner/repo (+ optional branch and sub-folder for a module inside a monorepo).
  3. Environment — which config/credentials set to use (dev / test / prod). Required — it never guesses.
  4. Deployed check — optionally look up what's actually running on Anypoint right now (by exact deployed name).
  5. Assess — figure out what needs to change and list any incompatible connectors. This is lean and fast: it shows what will change on the safe default with no slow network lookups.
  6. Version menu — only if you ask, it pulls a live per-connector menu (scoped to just your app's connectors).
  7. Strategy — you pick how to version them (safe default, latest, etc.).
  8. Dry run — show the exact plan. Nothing is written yet.
  9. Confirm — it waits for your clear “yes.”
  10. Execute — apply the changes and open a pull request.
  11. Track — follow the merge → tests → deployment and offer to roll back if a deploy fails.

Safety promise: the agent never changes code, never opens a PR, and never touches Anypoint until it has shown you a preview and you've explicitly approved it. This is enforced by a “dry-run gate” in the engine, not just by good manners.

1

Step 1 — Install Node.js

Node.js is the program that runs this toolkit. Open PowerShell (press the Windows key, type “PowerShell”, hit Enter) and check whether you already have it:

node -v

If it prints v18.x or higher, you're set. If it says the command isn't found, or shows an older number, download the LTS installer from nodejs.org, run it (Next through the defaults), then close and reopen PowerShell and check again.

2

Step 2 — Open a terminal in the toolkit folder

Everything is run from inside the toolkit folder (the “suite root”). In PowerShell, go there:

cd C:\Workspaces\7.25\mule-java17-upgrade-skills

You should now see that path at the start of your prompt. Leave this window open — you'll use it through Step 6.

Use PowerShell, not the old cmd.exe. Some commands pass a small piece of JSON; cmd.exe mangles the quotes (you'd see Unexpected token … is not valid JSON). PowerShell handles it correctly — and this guide prefers the discrete-flag form that avoids JSON entirely.

3

Step 3 — Install and self-check

Download the toolkit's one dependency, then run its built-in tests to prove the copy on your machine is healthy:

npm ci
npm test

npm ci downloads what's needed (js-yaml, about a minute). npm test runs the whole suite (a few hundred node --test cases) and should end with fail 0. This needs no key, no internet credentials, and changes nothing — it just confirms the code is intact.

If npm test reports failures, stop here and fix the install before going further (usually a wrong Node version — recheck Step 1). Don't wire Vibes onto a broken copy.

4

Step 4 — Create your .env settings file

.env is a small text file at the suite root holding two things: the decryption key and which environment to use. You create it once and never type these again — every script, CLI, and the server auto-load it (they walk up from their own location to find the suite-root .env, which is why symlinking skills matters later).

Make a copy of the provided template:

Copy-Item .env.example .env

Open the new .env (in VS Code or Notepad) and set these two lines:

MULE_CONFIG_KEY=<paste the AES key here>
MULE_UPGRADE_ENV=dev
  • MULE_CONFIG_KEY — the key that unlocks the saved credentials (a 16, 24, or 32-character string). Paste it with no quotes and no spaces. In the dev environment this one key wires all four integrations at once (Anypoint + GitHub + Jira + Slack), because their secrets ship pre-encrypted in config/config-secure-dev.yaml.
  • MULE_UPGRADE_ENV — which environment's settings to load. Use dev unless told otherwise. This is required — the toolkit fails fast rather than guess.

Verify it works (30 seconds)

From the suite root, run this one-liner. It never prints the secret — only a length and a yes/no:

node -e "import('./lib_shared/config.js').then(c=>{const e=c.requireEnv(process.env.MULE_UPGRADE_ENV,{flag:'MULE_UPGRADE_ENV'});console.log('env =',e,'| key length =',(process.env.MULE_CONFIG_KEY||'').length,'| github.token resolves =',c.has('github.token'));})"

You want to see something like env = dev | key length = 32 | github.token resolves = true. The true means the key successfully unlocked a credential — you're wired.

No AES key? Leave MULE_CONFIG_KEY empty and instead add plain-text lines — each overrides the encrypted YAML value: GITHUB_TOKEN=ghp_xxx (and, if you have them, ANYPOINT_CLIENT_ID, ANYPOINT_CLIENT_SECRET, SLACK_WEBHOOK_URL, JIRA_EMAIL, JIRA_API_TOKEN). You can mix (key for some, plaintext for others).

The saved credentials use MuleSoft's ![…] secure-property format (an IV-prefixed AES value). Keep the ![ and ] — removing them turns the value into unusable plain text. The AES key in .env must be the same key those values were encrypted with, or they decrypt to garbage. Never share or commit .env or the real key (it's already Git-ignored). Make sure the file is named exactly .env — Notepad may secretly save it as .env.txt (use “Save as type: All Files”).

5

Step 5 — Verify config & the four integrations (terminal)

Before touching Vibes, prove the credentials resolve and each live integration works from PowerShell. Every call here is non-fatal and env-gated — a missing/rotated secret prints a clear “skipped / unverified,” never a crash. Replace the sample repo/app names with your own.

5a — Config + matrix wiring (start here)

# Assess an app straight from GitHub (no download). --quiet emits JSON only:
node skills/mule-upgrade-assess/scripts/assess.js --source github `
  --owner acme --repo-name orders-api --branch main --env dev --quiet

In the JSON, check two things:

  • matrixSource is exchange:<version> — the compatibility matrix was pulled live from Anypoint Exchange (not the bundled fallback). Good. If it says bundled, your Anypoint credentials aren't decrypting (see Troubleshooting) — the assessment is still correct, just offline.
  • No giant HTML/YAML blob in warnings (that means an Anypoint call returned a login page — a token problem).

5b — GitHub (a real PR against a test repo)

node skills/mule-upgrade/scripts/upgrade.js start `
  --app orders-api --mode api --owner acme --repo-name orders-api --branch main --env dev

Success → a real PR and a job at PR_OPEN (note the job-… id). A 401/403 means the GitHub token is missing/rotated or lacks repo scope. makes a real PR

5c — Anypoint (read your Runtime Manager fleet)

node skills/mule-upgrade-scan/scripts/scan.js --env dev

If Anypoint creds resolve you get a fleet table; if not, rows report unverified (never a crash). Here --env is the Anypoint environment name(s) to scan (e.g. Production,Staging) — the config env comes from MULE_UPGRADE_ENV.

5d — Slack (dry-run first, then live)

node skills/mule-upgrade-scan/scripts/scan_notify.js --dry-run   # compute digest, send nothing
node skills/mule-upgrade-scan/scripts/scan_notify.js            # send to slack.webhookUrl (#java17-upgrades)

5e — Jira + Slack (opt in, once)

Both are silent by default — a configured webhook and Jira token make delivery possible, but someone still has to ask for it. So Step 5b posted nothing. Re-run it with the opt-in flags to see them fire:

node skills/mule-upgrade/scripts/upgrade.js start --app <app> --env dev --mode api \
  --owner <o> --repo-name <r> --branch develop \
  --jira-mode create --slack

--jira-mode create files a ticket in project J1U and comments “PR opened”; --jira-mode comment comments on the ticket you pass with --jira instead of creating one; --slack posts to slack.webhookUrl. Missing creds → a clean “no Jira creds” / “no SLACK_WEBHOOK_URL” skip.

In Vibes you won’t type these flags. The conductor asks you once, as the second intake question: paste a Jira ticket to update, say “auto” to have one created, or skip — plus a yes/no for Slack. It then obeys that for the rest of the session, including later apps and parent-pom runs, and never asks again. Because the answer is stamped on each job when it’s created, a job started with Slack off stays silent forever — even if a reconcile sweep discovers its deploy hours later from a different terminal.

If 5a shows matrixSource: exchange:…, 5b prints PR_OPEN with a link, and the scan returns live rows — all four integrations are wired. Now exercise each skill (Step 6), then wire Vibes.

6

Step 6 — Prove every skill from the terminal (in order)

This runs every skill's CLI end-to-end so the whole suite is exercised before Vibes. Run them in order — a few reuse the job-… id from an earlier step. Set your values once:

$REPO   = "C:\path\to\a-mule-4.6-to-4.8-java8or11-clone"  # a real target you can PR against (local mode)
$OWNER  = "acme"                                          # your GitHub owner (api mode)
$REPONAME = "orders-api"                                  # a repo you can push branches to (api mode)

Skill 1 — mule-upgrade-assess (read-only)

# offline & deterministic (bundled matrix, no network):
node skills/mule-upgrade-assess/scripts/assess.js --repo "$REPO" --no-fetch --quiet --out plan.json
# live (matrix fetch + Anypoint cross-checks in dev):
node skills/mule-upgrade-assess/scripts/assess.js --repo "$REPO" --env dev --quiet --out plan.json
# the connector version MENU (opt-in, slower — live Exchange + release-notes):
node skills/mule-upgrade-assess/scripts/assess.js --repo "$REPO" --env dev --versions --quiet
# is the matrix ITSELF stale? (advisory audit — the check_drift capability):
node skills/mule-upgrade-assess/scripts/lib/matrix_drift.js --connectors

Expect an AssessmentResult JSON (also saved to plan.json): current runtime/Java → target, changePlan.fileEdits[], connectorsInApp[], and any connectorGaps/missingFromMatrix.

Skill 2 — mule-upgrade orchestrator (opens a PR)

# ALWAYS dry-run first — writes nothing, prints PLAN_PREVIEW:
node skills/mule-upgrade/scripts/upgrade.js start `
  --app orders-api --env dev --mode api --owner "$OWNER" --repo-name "$REPONAME" --branch main --dry-run

# then execute (identical args, minus --dry-run, plus a strategy):
node skills/mule-upgrade/scripts/upgrade.js start `
  --app orders-api --env dev --mode api --owner "$OWNER" --repo-name "$REPONAME" --branch main --version-strategy min

Expect PR_OPEN with a PR link + job-… id (and, if wired, a J1U ticket + Slack post). Copy the id:

$JOB = "job-XXXXXXXX"   # from the output above

Skill 3 — mule-upgrade-apply (the internal rewriter)

Apply is what the orchestrator runs between assess and commit — Step 2 already exercised it live, and npm test covers it. To see it in isolation, feed plan.json from Skill 1 to a scratch copy of the repo:

node skills/mule-upgrade-apply/scripts/apply_edits.js --change-plan plan.json --repo "$REPO"    # preview staged blobs
# add --write to actually edit files in the clone

Skill 4 — mule-upgrade-job (status / list / reconcile / reapply / delete)

node skills/mule-upgrade-job/scripts/job.js status --job $JOB --refresh   # auto-refreshes live PR/CI/deploy
node skills/mule-upgrade-job/scripts/job.js get    --job $JOB             # raw record
node skills/mule-upgrade-job/scripts/job.js list                          # all jobs
node skills/mule-upgrade-job/scripts/job.js reconcile --stale-seconds 0   # sweep (standalone)
# admin (do these LAST — delete removes the record):
node skills/mule-upgrade-job/scripts/job.js reapply --job $JOB
node skills/mule-upgrade-job/scripts/job.js delete  --job $JOB

Skill 5 — mule-upgrade poll tail

node skills/mule-upgrade/scripts/upgrade.js poll --stale-seconds 0   # advance PR_OPEN → DEPLOYING → DEPLOYED
# continuous (dev convenience): node skills/mule-upgrade/scripts/upgrade.js poll --watch --interval 30

Skill 6 — mule-upgrade-parent-pom (shared parent/BOM)

# read-only: what does this pom inherit? (recommend BOM-first if it imports one)
node skills/mule-upgrade-parent-pom/scripts/parent_pom_cli.js `
  --repo-url https://github.com/$OWNER/mule-parent --env dev --detect-only
# upgrade it (pins connectors + minor-bumps its own version + opens a PR, or NO_CHANGE):
node skills/mule-upgrade-parent-pom/scripts/parent_pom_cli.js `
  --repo-url https://github.com/$OWNER/mule-parent --env dev --mode api

Skill 7 — mule-upgrade-pr rollback (revert PR)

# simplest path: roll back through the orchestrator/tool by job (it reads sha+branch from the record).
# raw CLI (needs coords + the upgrade commit sha + branch from `job.js get`):
node skills/mule-upgrade-pr/scripts/pr.js rollback --mode api `
  --coords '{"owner":"acme","repo":"orders-api","defaultBranch":"main"}' `
  --commit-sha <upgradeCommitSha> --branch <upgradeBranch> --app orders-api --job $JOB

Skill 8 — mule-upgrade-scan (fleet audit + proactive Slack)

node skills/mule-upgrade-scan/scripts/scan.js --env dev --json           # machine-readable fleet audit
node skills/mule-upgrade-scan/scripts/scan_notify.js --dry-run           # digest, no send
node skills/mule-upgrade-scan/scripts/scan_notify.js --always-notify     # full digest every run

Skill 9 — mule-upgrade-matrix-update (maintenance)

node skills/mule-upgrade-matrix-update/scripts/matrix_update_cli.js          # review proposed bumps (writes nothing)
node skills/mule-upgrade-matrix-update/scripts/matrix_update_cli.js --json   # machine-readable proposals
node skills/mule-upgrade-matrix-update/scripts/matrix_update_cli.js --apply  # adopt (the ONLY writer) then re-run npm test

When all nine behave — assess reads correctly, dry-run prints PLAN_PREVIEW, the real run prints PR_OPEN, status/poll advance the job, parent-pom + rollback + scan + matrix-update all respond — the toolkit is proven end-to-end. Now, and only now, wire Vibes.

7

Step 7 — Link all skills into Vibes

Vibes looks for skills in a folder called .a4drules/skills inside whatever project you have open. We point it at the toolkit's skills. The correct way is to “symlink” (create a shortcut), not copy — a copy would break because each skill reaches back into the suite for shared code (../../lib_shared) and your one .env.

7a — Turn on symlink permission (one time)

On Windows, creating a symlink needs either Developer Mode on (Settings → Privacy & security → For developers → Developer Mode) or a PowerShell window opened as Administrator. Do one of those, then continue.

7b — Create the shortcuts for all 9 skills

Open the Anypoint Code Builder workspace folder in PowerShell (the project you'll be working in), then run:

$SUITE = "C:\Workspaces\7.25\mule-java17-upgrade-skills"
New-Item -ItemType Directory -Force -Path .a4drules\skills | Out-Null
foreach ($s in "mule-upgrade-agent","mule-upgrade","mule-upgrade-assess","mule-upgrade-apply","mule-upgrade-pr","mule-upgrade-parent-pom","mule-upgrade-job","mule-upgrade-scan","mule-upgrade-matrix-update") {
  New-Item -ItemType SymbolicLink -Path ".a4drules\skills\$s" -Target "$SUITE\skills\$s" -Force
}

That links all 9 skills, including the star mule-upgrade-agent. You do not link mule-upgrade-mcp — that only describes the server. The -Force flag makes it safe to re-run whenever the skills change.

Global scope (optional). To make the skills available in every ACB workspace, link them into Vibes' global skills storage instead of a single workspace's .a4drules/skills. Workspace scope (above) is best for a project-pinned upgrade and is committable so the whole team gets them.

8

Step 8 — Reload Vibes and confirm it sees them

  1. Reload the Anypoint Code Builder window so Vibes re-scans for skills: Ctrl+Shift+P → “Reload Window” → Enter (or restart ACB).
  2. Open the Vibes Skills panel. You should see all 9 skills under “Workspace,” including mule-upgrade-agent.
  3. That's it — Vibes activates the right skill (via its use_skill tool) based on what you ask.

Whenever the toolkit is updated, re-run the link command in Step 7b (safe with -Force) and reload the window again so Vibes picks up the newest skills. If a skill behaves like an old version, an un-reloaded window is the usual cause.

9

Step 9 — Test EVERY skill in Vibes by chatting

This is the real test. Below is a per-skill runbook: for each skill, the exact thing to say, what it runs under the hood, what to expect, and how to verify. Do them roughly top to bottom — Skills 2/3 produce a job-… id that later skills reuse. A green tag read-only means it changes nothing; a red tag writes means it can open a PR or edit files (always after a preview + your yes).

How Vibes decides which skill to use: each skill's SKILL.md has trigger phrases. You don't name skills — you describe intent, and Vibes routes. For a guided upgrade it will pick mule-upgrade-agent; for “what's the status of job …” it picks mule-upgrade-job; and so on.

get the job and confirm the fields; a passing MUnit stays PR_OPEN (“MUnit passed” sub-stage) until the PR is merged.
Skill 6 · mule-upgrade-parent-pom writes

For apps whose connectors are pinned by a shared parent/BOM pom (usually in another repo). Test the read-only detect first, then the upgrade.

Say — detect (read-only)

“What does the parent pom at github.com/acme/mule-parent inherit? Don't change anything.”

Say — upgrade

“Upgrade the shared parent/BOM pom at github.com/acme/mule-parent for Java 17 (env dev).”

Runs
upgrade_parent_pom {detectOnly:true} then upgrade_parent_pom.
Expect
detect → DETECTED with its inheritance + edit preview (it will recommend upgrading a BOM first if it imports one). upgrade → PR_OPEN (pins connectors + minor-bumps its own version in one PR) or NO_CHANGE if already at the matrix. It's a tracked job — pollable like an app.
Verify
get_job_status shows kind: parentPomUpgrade. For a full app→parent→BOM chain, the agent (Skill 1) drives it and asks at each step.
Skill 7 · mule-upgrade-pr (rollback) writes

Opens a revert PR that restores the exact pre-upgrade file state. You don't need any coords — just the job.

Say to Vibes

“Roll back job job-….”

Runs
rollback (looks up the commit sha + branch from the job record for you).
Expect
A Revert: Java 17 upgrade <app> PR with {revertBranch, revertCommitSha, prUrl} — and a Slack note if wired.
Verify
The revert PR exists and its tree matches the pre-upgrade state.
Skill 8 · mule-upgrade-scan read + optional Slack

Turns the toolkit from reactive to proactive — find what's stale, and get alerted on change.

Say — audit

“Scan the fleet for apps still on old Mule/Java.”

Say — proactive

“Watch the fleet and alert me on Slack when new apps fall behind.”

Runs
scan_fleet then scan_notify.
Expect
A count + candidate list (each with the reason it was flagged and its GitHub repo, where known). scan_notify only posts to Slack when the stale set changes (de-duped) — so a timer won't re-spam.
Verify
Hand a resolved candidate straight to Skill 1/2 to upgrade it. Note: v1 scans CloudHub 2.0 / RTF only (see Risks in the technical doc).
Skill 9 · mule-upgrade-matrix-update writes rules file on --apply

Maintenance: adopt “the matrix is stale” advisories into the bundled compatibility matrix. Dry-run by default; only --apply writes.

Say — review

“Update the compatibility matrix — show me what would change first.”

Say — adopt

“Those look right — adopt the matrix bumps.”

Runs
matrix_update_cli.js (review) then --apply.
Expect
A from → to proposal list (gating pins move on their LTS line; connectors move latest-in-major, never across a breaking major). After apply, re-run npm test and commit the matrix change.
Verify
Only references/compatibility-matrix.yaml changed; comments preserved; lines that already moved are skipped, not clobbered.

Once all nine respond correctly by chat — the agent walks a full upgrade, assess/versions/drift report, apply previews cleanly, job status/reconcile advance, parent-pom + rollback open PRs, scan lists candidates, and matrix-update proposes bumps — your Vibes setup is fully working end-to-end. 🎉

Step 10 — Check it really worked

  • GitHub — the repo has a new pull request with the Java 17 changes (and a revert PR from Skill 7).
  • Status — ask “what's the status of the job?” It reports the stage (PR open → deploying → deployed) and how often to check again.
  • Jira (if wired) — a J1U ticket was created with a comment linking the PR.
  • Slack (if wired) — a PR-ready message (and the fleet digest from Skill 8) in #java17-upgrades.
  • Anypoint — the poll tail moved the job past PR_OPEN using a real deploy verify, and the scan returned live deployments.
  • Job store — inspect any run at ~/.mule-upgrade/jobs/*.json (override with MULE_UPGRADE_HOME).

Alternative — run it as an MCP server

If your Vibes setup blocks skills from running scripts, or you want the tools available over the network (e.g. for Agentforce) or event-driven CI/CD via the HMAC webhook, run the server instead of linking skills:

cd C:\Workspaces\7.25\mule-java17-upgrade-skills
$env:MCP_BEARER_TOKEN = "make-up-a-long-random-string"
node server/server.js       # listens on http://localhost:8080  (MCP JSON-RPC at POST /mcp)

Then in Vibes: MCP Servers → Remote Servers → Add, URL http://localhost:8080/mcp, header Authorization: Bearer <your token>. Reload — all 12 tools appear in the Installed tab with per-tool enable/auto-approve/timeout controls. It reads the same .env, so the same secrets decrypt. See SETUP-VIBES and SETUP-AGENTFORCE for details, and the technical deep-dive for the auth/webhook model.

Troubleshooting

You see…What it means & the fix
matrixSource: bundled (expected exchange:…)The live matrix couldn't be fetched — usually the Anypoint credentials aren't decrypting (wrong AES key, or the ![…] wrapper was stripped). Assessment still works off the bundled matrix; fix the creds to go live.
A big HTML / “document separator” blob in the warningsAn Anypoint call returned a login page instead of data — the client sent an empty/invalid token. Re-check that anypoint.clientId/clientSecret decrypt correctly.
Unexpected token … is not valid JSON on --coordsYou're in cmd.exe. Use PowerShell (single-quoted JSON passes literally), or drop --coords and use the discrete flags --owner/--repo-name/--branch.
A duplicated warning list in the Vibes chatThe assess ran without --quiet and both the JSON and the human summary got relayed. The agent uses --quiet; if you call assess directly, add it.
Skills don't appear in VibesYou copied instead of symlinked, or they're in the wrong place. They must be at .a4drules/skills/<name>/SKILL.md. Re-do Step 7 with symlinks and reload the window (Step 8).
Cannot find module '../../lib_shared/…'Same cause — a copied skill can't find the shared code. Symlink so it reaches back into the suite.
A skill behaves like an old versionThe window wasn't reloaded after an update. Re-run Step 7b (-Force) and reload (Step 8).
environment is requiredNo environment set. Put MULE_UPGRADE_ENV=dev in .env, or add --env dev. Check the file is .env, not .env.txt.
cannot decrypt secure property / “must be 16/24/32 characters”Wrong or empty AES key. Fix MULE_CONFIG_KEY, or use the plaintext-credentials option (Step 4 tip).
GitHub 401 / 403The token is missing or lacks permission. Add a valid GITHUB_TOKEN (needs repo scope), or gh auth login for local mode.
spawnSync gh ENOENT (local mode)The gh CLI couldn't be spawned on Windows. The branch still pushed; PR creation automatically falls back to the GitHub REST API using your token — so a working token is enough even without gh.
CONFLICT / UPGRADE_IN_PROGRESSAnother job holds the lock for that exact app/pom. It means “already done / in flight,” not “retry.” Surface the existing jobId/prUrl and stop.
Anypoint rows say “unverified” / deployed check skippedAnypoint credentials aren't set, or the deployed app name didn't match. Non-fatal — assessment still works; supply creds + the exact deployed name to enable it.
MCP server returns 401(Server option) The URL must end in /mcp and the Authorization: Bearer header must match MCP_BEARER_TOKEN.
The agent starts changing things without askingIt shouldn't — the design forbids it. Make sure you're talking to mule-upgrade-agent; it always dry-runs and asks before writing.

Glossary — every term explained

Java 17 / Mule 4.9.18 LTSThe newer versions every app must move to. Support for Java 8/11 is ending.
SkillA small helper with instructions the Vibes assistant runs on your behalf. This toolkit is a set of skills.
The agentThe mule-upgrade-agent skill — the chat conductor that walks you through the whole upgrade.
OrchestratorThe mule-upgrade skill — the non-interactive pipeline (assess → apply → commit → PR → track) the agent drives.
MCP server / MCP toolAn optional always-on service offering the same abilities as network “tools” (used to connect Agentforce). Each ability is one “tool.” Not needed for the skills path.
ConnectorA plug-in that lets a Mule app talk to something (HTTP, a database, Salesforce, Slack…). Old versions won't run on Java 17, so they get bumped.
Compatibility matrixThe toolkit's curated list of which versions are safe for Java 17. Pulled live from Anypoint Exchange when creds are set, else a bundled copy. The trusted source for “what version should this be.”
Connector gapA connector below the Java-17 pin whose version is controlled upstream (in a shared parent/BOM), so the app's own pom can't fix it. Needs the parent-pom skill.
Matrix drift (check_drift)An advisory audit of whether the matrix itself has fallen behind newer published versions. It only reports; mule-upgrade-matrix-update is what adopts the bumps.
AssessReading the app and figuring out what needs to change — without changing anything.
Dry run / PLAN_PREVIEWA full preview of the plan that writes nothing. Always shown before any real change.
Version strategyHow to pick each connector's new version: min (safe default), first-compatible, in-major, latest, or manual.
Parent POM / BOMA shared build file many apps inherit versions from. If your app uses one, mule-upgrade-parent-pom upgrades it in its own repo.
Pull request (PR)A proposed change on GitHub that a human reviews and merges. The agent opens one; it never merges on its own.
JobOne tracked upgrade. It moves through stages: PR open → deploying → deployed (or a failure stage).
ReconcileA sweep that advances stale jobs by polling GitHub + Anypoint (skills can't host a webhook listener, so they poll).
Anypoint / Runtime Manager (ARM)MuleSoft's cloud where apps are deployed. The agent can read what's currently running there (runtime/Java, not connector versions).
Environment (dev / test / prod)Which config + credentials to use. You must choose one — the toolkit won't guess.
.envYour private settings file at the suite root, holding the decryption key and chosen environment. Never shared.
AES key (MULE_CONFIG_KEY)The one password that unlocks the saved (encrypted) credentials.
SymlinkA shortcut that points to the real folder. We use it so Vibes sees the skills while they stay inside the toolkit (and can reach the shared code + .env).
RollbackUndo — the agent can open a revert pull request if a deployment fails.
