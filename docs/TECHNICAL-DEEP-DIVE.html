1. The problem & why it's hard

MuleSoft applications built on Java 8 or 11 must migrate to Java 17 on the Mule 4.9.18 LTS runtime before the old lines fall out of support. Across a fleet of dozens or hundreds of apps, doing this by hand is slow, repetitive, and dangerously easy to get subtly wrong.

A single app upgrade touches many coordinated points, each with its own rules:

The pom chainRuntime + Java properties, compiler source/target, the mule-maven-plugin, MUnit runner/extensions, and every incompatible connector — some pinned in the app, some inherited from a shared parent/BOM.
mule-artifact.jsonminMuleVersion and javaSpecificationVersions must be raised (never downgraded).
CI workflowsactions/setup-java versions, and JPMS --add-opens argLines the 4.9 container rejects on Java 17.
Which version is safe?Every connector has a minimum Java-17-safe version. “Latest” may be a breaking major. This knowledge lives on scattered release-notes pages.
Shared inheritanceIf connectors are managed by a parent-pom/BOM (often in a different repo), the app pom cannot fix them — the shared pom must move first, in order.
The tailOpen a PR, wait for review + CI (MUnit, dependency guard), merge, deploy, verify on Anypoint, and roll back if the deploy fails.

A naïve script that regex-bumps versions misses custom Java sources, DataWeave POJOs, matrix java: blocks in CI, and inherited connector gaps — and it can't have a safe conversation with a human about trade-offs. The goal was an agentic system: it reasons about the request, runs deterministic tooling, and keeps a human in control of every write.

Heritage. This suite is a skill-native re-implementation of an internal MuleSoft app, the Platform Lifecycle Orchestrator (a Mule 4.9.18 REST API + 6 MCP tools). Every rewrite, the rules engine, the job state machine, and the atomic-commit GitHub sequence were ported faithfully, then improved (full-clone assessment, explained edits, a synchronous run + polling tail instead of an async worker).

2. Solution at a glance

The system is a suite of 10 composable skills (9 you run + 1 that documents the server) sharing one deterministic engine, fronted by a conversational agent, and optionally exposed as a hosted MCP + REST server with the identical 12 tools.

Agentic, not a botA human-in-the-loop conductor gathers inputs, assesses, previews, and waits for an explicit “go” before anything is written.
Deterministic engineThe LLM never invents versions or edits. A rules engine + a curated compatibility matrix produce a byte-level change plan; the LLM narrates and orchestrates.
Safe by constructionA dry-run gate, single-flight locks, a stale-plan guard, and non-fatal integrations mean the worst case is “nothing happened, here's why.”
Two runtimes, one codebaseRun as IDE skills (Claude Code / Vibes, no server) or as a hosted server for remote agents (Agentforce) + event-driven CI/CD.

3. System context & the two runtimes

The exact same skill scripts and job store back both deployment shapes. You pick a runtime per situation; nothing about the engine changes.

Runtime A — IDE skills (default)

Claude Code or MuleSoft Vibes invokes the skills against a local clone or the GitHub API. Merge/CI/deploy detection is polling (gh + a token + Anypoint verify). No server, no open ports. Best for hands-on, project-pinned upgrades.

Runtime B — Hosted MCP + REST server

server/server.js exposes the same 12 tools over MCP JSON-RPC (POST /mcp) and a REST facade (/api/v1/tools/*), guarded by a bearer token, plus HMAC-verified CI/CD webhooks (POST /webhook/cd-result) that drive the state machine without polling. Best for remote agents (Agentforce) and event-driven CD.

Why this matters: a skill cannot host a long-lived webhook listener, so in Runtime A the deploy tail is polled. When you want true event-driven CD, Runtime B adds the inbound webhook — but both share one engine and one ~/.mule-upgrade/ JSON job store, so you can even mix them (skills for assess/upgrade, server for the webhook-driven tail).

4. Agent architecture & design choices

The architecture is a three-layer composition: a conversational conductor on top, a non-interactive orchestrator in the middle, and single-purpose worker skills underneath — all sharing common libraries and a durable job store.

Figure 2 — Layered composition. The conductor talks to people; the orchestrator runs the pipeline; workers do one thing each; everything reads shared libs, the matrix, and the job store. The server is a thin transport over the same handlers.

4.1 The conductor: a human-in-the-loop state machine

The mule-upgrade-agent skill is the primary entry point for any person. It's not a free-form chatbot — its SKILL.md encodes an 11-step state machine that the host LLM must follow in order, asking rather than inventing at every step:

Figure 3 — The conductor's 11-step conversation. Steps 5–7 are read-only; steps 8–9 are the safety gate; only step 10 writes.

Why a conductor at all?

Every worker skill is non-interactive: given inputs, it runs to completion. That's perfect for scripts and CI, but a person needs to be asked (which repo? which env? which version strategy?) and shown a preview before a PR is opened. The conductor supplies exactly that missing conversation — nothing more. It's a thin layer that routes intent to the same CLIs/tools the orchestrator exposes, so there's no second implementation to keep in sync.

4.2 The prime directive: preview before you write

The single most important design choice is that nothing is written until the user has seen a dry-run plan and explicitly confirmed. “Writing” means acquiring the app lock, creating a job, editing a file, or opening a PR. The mechanism is the dryRun flag on start_upgrade:

  • dryRun: true → runs assessment, builds the full plan (file edits, connector choices, warnings, deployed-state), returns PLAN_PREVIEW, and writes nothing — no lock, no job, no edit, no PR.
  • dryRun: false → executes the pipeline and opens the PR.

The agent always calls dry-run first, shows the preview, gets an unambiguous yes, then re-calls with the identical arguments and dryRun:false. This is verified by a test that asserts a dry run acquires no lock, creates no job, and never reaches apply/commit.

4.3 The execution contract: act only through the engine

Because a capable LLM will happily “help” by hand-editing a pom or guessing a version, the skills carry an explicit, non-negotiable execution contract baked into their instructions. The agent may never:

  • hand-write, hand-edit, or simulate a pom.xml / mule-artifact.json / CI workflow / ChangePlan / PLAN_PREVIEW — the engine produces these; the agent reports what it returns;
  • invent, guess, or “reason out” connector/runtime/plugin versions — the compatibility matrix is the sole authority;
  • call GitHub itself (curl, gh api, fetching a repo) or ask the user to paste a pom or a token in chat — the engine reads the repo;
  • modify, patch, or work around the suite's own source — even if it believes it found a bug. A command error is a valid final result: report it verbatim and stop.

Design value: this contract is what makes an LLM-driven system trustworthy for production changes. The LLM's creativity is confined to conversation and narration; all consequential decisions are deterministic engine output. Determinism where it matters, flexibility where it's safe.

4.4 Why skills-native (and not a monolith or a pile of prompts)?

5. Tools, frameworks, platforms & models

5.1 Runtime & language

  • Node.js ≥ 18 (developed on v24), ES modules throughout. The only runtime dependency is js-yaml — everything else (HTTP, crypto, file I/O, child processes) uses the Node standard library. This keeps the supply chain tiny and the install trivial (npm ci).
  • Dependency-free HTTP via the global fetch (Node 18+) for GitHub/Anypoint/Jira/Slack, and execFile-style child processes for git/gh (never a shell string — see Security).

5.2 The agent/model layer

The system is deliberately model-agnostic. There is no hard-coded model; the “intelligence” is whatever host LLM drives the skills or the MCP tools:

  • Claude Code (IDE) and MuleSoft Vibes (Anypoint Code Builder) natively speak the Agent Skills / SKILL.md format and auto-invoke a skill by trigger phrase via their use_skill tool.
  • Agentforce (or any MCP client) drives the hosted server's 12 tools over MCP JSON-RPC / REST.

The model's job is narrow: interpret intent, drive the 11-step conversation, and turn structured JSON into readable prose. All facts come from the engine. This is why the same suite runs identically under different models — the correctness lives in the engine, not the prompt.

5.3 Protocols & integration surfaces

6. The engine internals (deep)

The heart of the system. This is where “Java 17 upgrade” becomes a precise, byte-level set of edits, a PR, and a tracked lifecycle.

Figure 4 — The one-shot pipeline (port of pf-start-upgrade). Runs to PR_OPEN in a single call; the deploy tail is a separate polling step.

6.1 Assessment — from repo to ChangePlan

mule-upgrade-assess is a faithful Node port of the Mule app's assessment DataWeave, plus a dynamic matrix fetch the original couldn't do inline. It:

  1. Walks the pom inheritance chain (app → parent → BOM), re-parsing each pom from raw text so repeated <dependency>/<plugin> elements survive (a Map parse would collapse duplicates and silently drop pins).
  2. Classifies topology — APP_STANDALONE / PARENT_APP / BOM_PARENT_APP / MULTI_LEVEL — from chain depth + top-of-chain dependencyManagement.
  3. Applies the compatibility matrix (§6.2) to emit a byte-level ChangePlan.fileEdits[] with a fixed kind per edit (pomProperty, depVersion, pluginVersion, muleArtifactJson, ciWorkflow, munitRuntimeVersion, munitArgLines, pomVersion).
  4. Emits connectorsInApp[] (each app connector's current version, matrix pin, willChange) network-free, always; connectorGaps[] (below-target connectors pinned upstream, unfixable in the app pom); and missingFromMatrix[] (declared but uncovered) — the last two are surfaced as human-judgement items.
  5. Optionally does a verbatim deployed-state check against ARM (exact name match, cross-environment fallback), reporting the running runtime/Java — always with a stated reason when skipped.

Lean by default (the “Full Split”). A plain assess returns in ~1–3s with the network-free plan. The two slow, advisory features are opt-in tools so the common path stays fast: the per-connector version menu (resolve_versions) and the matrix-drift audit (check_drift).

6.2 The compatibility matrix — hybrid, dynamic + static

Figure 5 — The hybrid matrix: static gating pins stay authoritative; live Exchange/release-notes data enriches a version menu and a drift advisory but never replaces the curated floor. Any fetch failure silently falls back to the bundled YAML.

The split is deliberate: gating versions (runtime patch, mule-maven-plugin, MUnit runner/extensions, compiler source/target) encode a minimum required for Java 17 — a policy floor that doesn't live on connector release-notes pages, so it stays static and authoritative. Connector versions are enriched live (highest-in-major, latest, and the first Java-17-safe version parsed from each release-note's OpenJDK compatibility row), but the curated pin is the default and “latest” is never auto-adopted (it may be a breaking major).

Three caching layers keep repeated runs fast and non-fatal: the Anypoint bearer token, the Exchange matrix fetch, per-connector listVersions, and a ~24h disk cache of release-notes pages (~/.mule-upgrade/matrix-cache.json). A missing/corrupt cache silently degrades to a live fetch.

6.3 The 8 byte-preserving rewrites

mule-upgrade-apply consumes the ChangePlan and applies edits grouped by file in a fixed order:

depVersion → pluginVersion → pomProperty → munitRuntimeVersion
→ muleArtifactJson → ciWorkflow → munitArgLines → pomVersion

Every rewrite is byte-preserving: only the targeted value changes — comments, ordering, indentation, and unrelated elements are left exactly as-is (no YAML/XML round-trip through a dumper that would reflow the file). The appOverride strategy writes each version edit into the app's own module pom so sibling modules sharing a parent/BOM are never touched. This byte-fidelity is what makes the PR diff reviewable — a human sees only the intended change.

6.4 Commit + PR — atomic, with a stale-plan guard

mule-upgrade-pr ports the Git flows into two interchangeable modes:

api mode (default)

Pure GitHub Git Data API: create a branch ref at the assessed headSha, one blob per file, a tree with base_tree=headSha, a commit with parents=[headSha], move the ref, open the PR. Fully atomic; never touches a working copy — the exact byte-level commit, reproducibly.

local mode

git checkout -b → write files → commit → push → open the PR. PR creation tries the gh CLI and automatically falls back to the REST API if gh can't be spawned (the common Windows spawnSync gh ENOENT), so a token alone is enough. Returns a prNumber so local jobs are pollable like api-mode ones.

Both enforce the stale-plan guard: if the repo HEAD moved since assessment, they raise STALE_PLAN rather than commit a stale plan onto newer work. Branch names are collision-free: migrate/<app>-<runtime>-java<java>, then -1..-50, then -<jobId>. Rollback recreates the pre-upgrade parent's tree on a fresh revert/ branch — immune to intervening unrelated changes.

6.5 The job store & state machine

mule-upgrade-job is a dependency-free JSON re-implementation of the Mule app's Object Store, with four partitions under ~/.mule-upgrade/ (override via MULE_UPGRADE_HOME):

PartitionKeyPurpose
jobs/<jobId>.jsonjob-<uuid>the job record (status, coords, changePlan, PR, timestamps, error)
locks/…per-modulesingle-flight lock; value = jobId (lockKey = <repo>::<pomPath>)
index/…branch namebranch → jobId correlation for the reconcile/poll tail
idem/…delivery/poll keyidempotency markers so a repeated webhook/poll doesn't re-transition

Keys containing :// are encoded to a safe filename stem + short hash. Writes are atomic (temp file + rename); locks and idempotency markers use exclusive create (wx) so contention is detected without a read-modify-write race — crash-safe by construction.

Figure 6 — The job state machine (ported verbatim). On any pipeline error the job goes terminal and the lock is released; a manually-closed PR is detected too (→ CLOSED).

6.6 Reconcile — polling, not webhooks (in skills mode)

A skill can't host a listener, so reconcile polls external state for every stale job: a stale PR_OPEN polls the PR (merged → DEPLOYING; closed-unmerged → CLOSED + lock release; still open → untouched); a stale DEPLOYING verifies the deploy on Anypoint (healthy → DEPLOYED, else FAILED_DEPLOY); a stale early-stage job is treated as orphaned → FAILED_INTERRUPTED + lock release. Even jobs parked at MUNIT_FAILED/DEP_GUARD_FAILED re-poll the PR, so a manual close is reflected. The pollers, deploy verifier, and notifier are all injectable, so the sweep is pure and unit-tested. In server mode, the same transitions are driven by the HMAC webhook instead.

6.7 Chained parent → BOM → app upgrades

Most apps are standalone. But when the app assess reports connectorGaps, the incompatible connectors are pinned upstream and the app pom can't fix them. The suite handles the three real-world topologies, upgrading upstream first so the app PR's first commit already repoints its <parent>:

Figure 7 — The three topologies. Each pom is a tracked job locked per-module; the agent stops and asks at every arrow. “Upgrade the app LAST” folds the parent repoint into the app PR's first commit.

6.8 Proactive fleet scan

mule-upgrade-scan turns the system from reactive to proactive: it enumerates AMC deployments across environments, classifies each app stale (Mule below a threshold or Java below 17), maps it to a GitHub repo (registry → request → convention), and de-dups across environments. scan_notify diffs against a remembered baseline and pushes a Slack alert only when the stale set changes — so a 15-minute timer reports change, not steady state.

7. Prompting & instruction design

Because the model is the conversational driver, the instruction design lives in each skill's SKILL.md — the frontmatter and prose are the prompt. Key techniques:

  • Trigger-phrase routing. Each SKILL.md frontmatter has a name and a description full of natural trigger phrases (“upgrade mule app to java 17”, “what's the status of job …”, “scan the fleet”). The host auto-invokes the right skill from intent. The conductor's description explicitly positions it as the default human entry point, so a plain request routes to the guided flow, not the raw pipeline.
  • The execution contract as a hard prompt. The “act only through the engine; never guess versions; never hand-edit; a command error is the final answer” rules (§4.3) are stated up front and non-negotiable — this is what prevents hallucinated poms/versions.
  • Explicit state machine. The 11 steps are enumerated with per-step prompts, so the model asks in the right order and never invents a missing input (env is required; it must ask).
  • “Present results as prose, never echo raw output.” The agent is told to pass --quiet (JSON-only) and write a short human summary — this eliminated a real bug where relaying both the JSON and the CLI's human summary produced a duplicated warning list.
  • Guardrails baked in: confirm before executing; treat CONFLICT as “already done, stop”; raise connectorGaps/missingFromMatrix as human-judgement items; never print secrets; collapse noisy “using bundled matrix” warnings into one calm sentence.
  • Anti-self-modification. The suite's own source is READ-ONLY to the agent — even if it believes it found a bug — so it can't “fix” the engine mid-conversation. Defects go through the maintainer.

Design principle: constrain the model to do only what it's good at (understanding intent, conversing, summarizing) and forbid it from doing what it's bad at (precise, consequential edits). The prompt is a contract, not a suggestion.

8. Security & access considerations

Figure 8 — Two separate auth paths: a constant-time bearer guard for tool calls, and HMAC-SHA256 over exact bytes for CI/CD webhooks. Inputs are schema-validated; secrets never reach the transcript.

Secrets management

  • MuleSoft secure-property format. Credentials ship AES-encrypted as ![…] (IV-prefixed) in config-secure-<env>.yaml. One key (MULE_CONFIG_KEY) decrypts them at runtime; per-env keys (MULE_CONFIG_KEY_<ENV>) are supported for the day an env is re-encrypted separately.
  • Plaintext override precedence. Every client resolves a secret as: plaintext env var → decrypted YAML → default. So you can rotate a single credential without the key.
  • Never leak. Guardrails forbid printing decrypted secrets or the decryption key to stdout/transcript; .env is git-ignored; .env.example keeps the key empty.

Transport & access

  • Bearer auth (MCP_BEARER_TOKEN) protects /mcp + /api/v1/* with a constant-time compare; unset = open (local dev only). TLS is expected in front for remote hosts.
  • HMAC-SHA256 (GITHUB_WEBHOOK_SECRET) authenticates CI/CD webhooks over the exact received bytes, with delivery de-dup via idempotency markers so a replayed delivery can't re-transition a job.
  • Schema-contract guard. Every tool input is validated against its JSON Schema before the handler runs — a violation is a protocol error, never a half-applied action.
  • Least privilege: GitHub token needs only repo scope; the Anypoint connected app needs Runtime/API-Manager read; Slack is a single webhook URL.

Change-safety controls (security of the action, not just the transport)

  • Shell safety: git/gh are invoked via execFile-style calls — inputs are arguments, never interpolated into a shell string (no command injection).
  • Stale-plan guard: a commit aborts if the branch moved since assessment, so a stale plan is never applied over newer work.
  • Human-gated writes: the dry-run gate + explicit confirmation mean no unreviewed change reaches a repo; the PR is opened but never merged by the agent.
  • Non-fatal integrations: a missing/rotated credential or an outage is logged and skipped with a reason — it degrades cleanly instead of failing the pipeline or leaking a stack trace of internals.

9. Scalability considerations

Per-module single-flight locksLocks are keyed <repo>::<pomPath>, so different apps/modules never block each other. A monorepo can have its BOM, parent, and app PRs open at once; a second run of the same pom returns CONFLICT (“already in flight”).
Stateless engine + durable storeThe engine holds no in-memory session; all durable state is atomic JSON files. Many upgrades across many repos run independently and in parallel.
Caching everywhere it paysAnypoint token, Exchange matrix, per-connector listVersions, and a ~24h release-notes disk cache — cross-process, file-per-key, and fully non-fatal. A multi-connector assess + upgrade won't re-download the same pages.
Lean-by-default assessmentThe common path skips all live version/drift fetches (~1–3s); the slow, advisory lookups are opt-in tools. Fast where it's used most.
Polling ↔ event-drivenSkills mode polls the deploy tail (fine for tens of jobs on a timer); server mode adds the HMAC webhook for event-driven CD at fleet scale without polling.
Fleet scale, de-dupedscan_fleet enumerates the whole org; scan_notify only alerts on change, so a frequent schedule doesn't spam. The server is a thin transport, so it scales horizontally behind a load balancer.

10. Reusability & maintainability

  • Composable, single-responsibility skills. Each does one thing and is usable à la carte or composed. New capability = new skill, not a fork.
  • One engine, two transports. The CLIs and the server tools call the same handlers; server/schemas/*.json are the single source of truth for every tool's input (MCP tools/list, the REST facade, and validation all read them). No drift between IDE and server behavior.
  • Data-driven rules. The compatibility matrix, the connector notes-map (artifactId → release-notes URL), and the app-registry are YAML data files. Tuning the upgrade policy is editing data, not code — and mule-upgrade-matrix-update maintains the matrix safely (text-preserving, guarded, dry-run by default).
  • Injectable dependencies. The orchestrator, PR client, reconcile pollers, deploy verifier, and notifiers are all injectable, so the whole pipeline is unit-testable with zero network. This is both a testing win and a maintainability win (swap an integration without touching the core).
  • Byte-preserving rewrites. No reflow means small, reviewable diffs and no accidental churn — the code stays maintainable because its output is legible.
  • Docs per skill. Every skill's SKILL.md documents flags, outcome objects, and exit codes; AGENTS.md is the operating contract; the docs folder has setup + live-integration runbooks.

11. Testing approach

Testing is layered, deterministic, and offline-first — a direct consequence of the injectable-deps design.

  • Unit + behavior suites via the built-in node --test runner (npm test), one suite per skill: assessment, rewrites, PR/Git-Data sequence, job store + state machine, reconcile, orchestrate, parent-pom, scan, server. Several hundred tests, all runnable with no secrets and no network.
  • MUnit parity. The Mule app's MUnit cases (e.g. the DataWeave assessment suite, the GitHub atomic-commit/open-PR/rollback suite, the job-status suite) are ported 1:1 as Node tests, so the port is provably faithful.
  • Golden + guard tests for the rewrites (exact from → to, byte-preservation), the dry-run gate (no lock/job/edit on dryRun:true), the state-machine transitions, the stale-plan conflict, branch-collision suffixing, and the local-mode gh→REST fallback.
  • Injected fetch/pollers make every network path deterministic — the Git Data API endpoint order is asserted, reconcile transitions are driven by injected pollers with a fixed clock.
  • Two-phase manual verification (documented runbooks): first prove every skill from the terminal (offline, then live), then repeat the same functions inside Vibes — isolating “is the toolkit healthy?” from “is Vibes wired?”.

Primary-scenario evidence: the happy path (assess → PR_OPEN), the already-upgraded short-circuit, CONFLICT on a held lock, the FAILED_ASSESS/FAILED_COMMIT taxonomy with lock release, and the deploy-tail transitions are all covered by tests and exercised live in the runbook (real PR, Jira ticket, Slack post, poll advancing the job, rollback/reapply/delete).

14. The MVP

A working, demonstrable, technically sound agent-enabled workflow that upgrades a MuleSoft app to Java 17 end-to-end, with a human in control.

14.1 The working agent / workflow

The MVP is the mule-upgrade-agent conductor driving the full pipeline, runnable today in Claude Code or MuleSoft Vibes (skills) or via the hosted MCP server (Agentforce). The core use case — “help me upgrade a Mule app to Java 17” — runs through assess → version choice → dry-run preview → confirm → PR → track, and can chain a shared parent-pom/BOM when required.

14.2 Clearly defined input and output

Inputs

  • Source: local clone path, or api owner/repo (+ branch, + optional module sub-path).
  • Environment: dev|test|prod (required — selects config + credentials).
  • Deployed name (optional): for the verbatim ARM check.
  • Version strategy: min (default) · first-compatible · in-major · latest · manual.
  • Confirmation: an explicit “yes” after the dry-run.

Outputs

  • Assessment: current → target runtime/Java, the file-edit list, connectorsInApp[], connectorGaps, warnings.
  • PLAN_PREVIEW: the exact plan (nothing written).
  • PR_OPEN: {jobId, branchName, commitSha, prNumber, prUrl} + Jira ticket + Slack post.
  • Job status: stage + sub-checks + nextPollSeconds, advancing PR open → deploying → deployed.
  • On failure: a terminal status with a reason + an offered rollback.

14.3 Demonstration of the main use case

See the beginner guide, Step 9 for the full chat transcript and a per-skill runbook. In short: the operator says “upgrade orders-api to Java 17,” answers a few questions, reviews the dry-run plan, says “yes,” and receives a real PR link + job id; the agent then tracks the merge/CI/deploy and offers rollback if the deploy fails.

14.4 Assumptions & limitations

  • Target is Mule 4.9.18 LTS / Java 17; the compatibility matrix encodes the safe pins.
  • The operator has GitHub access (token or gh) and, for live features, Anypoint/Jira/Slack credentials — all optional and non-fatal if absent.
  • The agent opens a PR; a human reviews, merges, and owns the production deploy decision.
  • Fleet scan currently covers CloudHub 2.0 / Runtime Fabric; deployed-state doesn't expose connector versions (see §12).

14.5 Evidence the MVP has been tested for the primary scenarios

  • Automated: several hundred node --test cases (many ported 1:1 from the original app's MUnit suites) cover assessment, the eight rewrites, the Git Data API commit/PR/rollback sequence, the job state machine, reconcile transitions, the dry-run gate, and the parent-pom flow — all deterministic and offline.
  • Live end-to-end: the live-integration runbook exercises every skill against real GitHub/Anypoint/Jira/Slack (real PR opened, J1U ticket created, Slack posted, poll advancing the job, rollback/reapply/delete), then repeats the same functions inside Vibes.
  • Failure modes verified: 401 credentials, STALE_PLAN, CONFLICT, manual PR close (→ CLOSED), and the Windows gh→REST fallback are all handled and reported verbatim rather than routed around.

Bottom line: the MVP is functional, demonstrable, and technically sound — a deterministic engine wrapped in a safe, conversational agent, with automated tests and a live runbook proving the primary scenarios.
